# Design Decisions

> Chronological log of design decisions made for Blitzlist. Each entry captures
> what was decided, alternatives considered, rationale, and who decided.
>
> The skill `.claude/skills/track-decisions.md` enforces that new decisions
> made in future sessions get appended here.

## Format

Each decision is one section with a `### YYYY-MM-DD — Decision name` heading and these fields:

- **Decision:** What was actually chosen.
- **Alternatives considered:** What we evaluated and rejected, with one-line "why not."
- **Rationale:** Why the chosen option wins.
- **Decided by:** Who made the call (typically malte, with Claude as proposer).
- **Status:** `active` | `superseded by <decision>` | `revisited` (when applicable).
- **References:** Files/sections that codify the decision, links to issues/items.

Keep entries terse — link to long-form docs rather than restating them here.

## 2026-05-21 — Project initiation

- **Decision:** Build Blitzlist as an MCP-native AI-first shared workspace for hybrid human-agent teams.
- **Alternatives considered:** Build a Notion plugin instead (rejected: ecosystem dependency); build a Linear competitor (rejected: too narrow); build an MCP-only library (rejected: misses stakeholder layer).
- **Rationale:** The "list" primitive is universal across every era of work, but the AI era has no purpose-built list layer. Founder has direct experience (ProSiebenSat.1 ActionList → founded companies → product teams → AI agent work → personal life).
- **Decided by:** malte.
- **Status:** active.
- **References:** [PITCHES.md](./PITCHES.md), [README.md](./README.md).

## 2026-05-27 — All-Cloudflare hosting stack

- **Decision:** v1 ships entirely on Cloudflare — Workers (Hono) for API/MCP/OAuth, D1 (SQLite) for DB, Durable Objects for real-time WebSocket fanout, R2 for attachments (zero egress), KV for OAuth ephemeral state, Queues for async work, Pages for web app.
- **Alternatives considered:**
  - Full Vercel (Next.js + Vercel Functions + Neon Postgres): rejected — Workers cold starts beat Vercel for MCP latency; R2 egress economics matter at scale; Cloudflare actively ships MCP tooling (`workers-oauth-provider`).
  - Hybrid Cloudflare + Vercel + Supabase: rejected — too complex; three deploy pipelines for an early-stage product.
  - AWS Lambda + RDS: rejected — too much infrastructure for v1.
- **Rationale:** One vendor, one CI pipeline, one secret store. Hono is born on Workers (native, not adapter). MCP-as-platform is Cloudflare's stated direction (partnership with Anthropic). Migration path documented (web → Vercel if Pages roughness bites).
- **Decided by:** malte.
- **Status:** active.
- **References:** [ARCHITECTURE.md §2, §8, §16](./ARCHITECTURE.md).

## 2026-05-27 — Hono framework (over Express, Fastify, Next.js routes)

- **Decision:** Use Hono for the API + MCP server.
- **Alternatives considered:** Express (rejected: Node-era, requires shim on Workers); Fastify (rejected: same); Next.js API routes (rejected: tied to Vercel); raw Workers fetch (rejected: no middleware/routing primitives).
- **Rationale:** Hono is web-standards (Request/Response), runs natively on Workers, Cloudflare's recommended framework. Portable to any modern runtime if we ever leave Cloudflare.
- **Decided by:** malte.
- **Status:** active.
- **References:** [apps/api/src/index.ts](./apps/api/src/index.ts).

## 2026-05-27 — Monorepo with pnpm + Turborepo

- **Decision:** TypeScript monorepo with pnpm workspaces + Turborepo. Apps in `apps/`, shared code in `packages/{db, core, mcp, ui}`.
- **Alternatives considered:** Nx (rejected: heavier); single repo, no workspaces (rejected: lose shared types); Lerna (rejected: legacy).
- **Rationale:** pnpm is fast and disk-efficient; Turborepo caches across the task graph; standard pattern in modern TS shops.
- **Decided by:** malte.
- **Status:** active.
- **References:** [package.json](./package.json), [turbo.json](./turbo.json), [pnpm-workspace.yaml](./pnpm-workspace.yaml).

## 2026-05-28 — Drizzle ORM for D1 (with SQLite dialect)

- **Decision:** Use Drizzle ORM with the `drizzle-orm/d1` dialect; migrations generated by drizzle-kit, applied via wrangler.
- **Alternatives considered:** Kysely (rejected: less integrated with D1); Prisma (rejected: heavy runtime, poor Workers fit); raw SQL only (rejected: lose type safety).
- **Rationale:** Type-safe schema definitions, generates D1-compatible migrations, dialect can swap to Postgres later if we outgrow D1's ceiling without rewriting application code.
- **Decided by:** malte.
- **Status:** active.
- **References:** [packages/db/src/schema.ts](./packages/db/src/schema.ts), [packages/db/drizzle.config.ts](./packages/db/drizzle.config.ts).

## 2026-05-28 — Generic polymorphic `relations` table (not typed `item_relations`)

- **Decision:** Single `relations` table with free-text labels, polymorphic endpoints (item / document / file / group / external URL on either side).
- **Alternatives considered:** Typed `item_relations` table with enum types (rejected: rigid; new label = migration); separate `item_sources` table for provenance (rejected: redundant with polymorphic relations).
- **Rationale:** User explicitly asked for the ability to "link everything with everything" with free-text labels. Provenance chains (call → item → PR → deploy → release notes) all query against ONE table. Workspaces extend the vocabulary without schema changes.
- **Decided by:** malte (after Claude proposed typed `item_sources`).
- **Status:** active (not yet implemented — lands in BL-026 during v0.5).
- **References:** [ARCHITECTURE.md §3 "Relation labels"](./ARCHITECTURE.md), [BL-026](./blitzlist/items/BL-026-generic-relations.md).

## 2026-05-29 — Brand: Blitzlist (umbrella) + Blitzbox (named module)

- **Decision:** Blitzlist is the parent brand AND the flagship integrated workspace product. Blitzbox is a named module inside, with standalone marketing-surface potential for v1.5+.

- **Rationale:** Notion-style umbrella+flagship pattern. Blitzbox can win the "AI-native file sharing" category independently when v1.5 ships; until then it's a feature of Blitzlist.
- **Decided by:** malte (after multiple rounds of brainstorming).
- **Status:** active.

## 2026-05-29 — Compass: flexible slot/metric mapping with type-bridging

- **Decision:** The Compass has fixed visual slots (in code) and flexible metrics (per-workspace). Per-list `compass_config` maps slots → metrics with explicit bridging for type mismatches (continuous→continuous direct, enum→discrete `value_map`, enum→continuous ordered or `value_map`, continuous→discrete `buckets`). Validation happens at config-save time, not render time. Shapes (sphere/cube/cylinder/star/cone), patterns, borders are discrete slots.
- **Alternatives considered:** Fixed-column `item_scores` table with hardcoded dimensions like importance/urgency/risk (rejected: rigid; different domains need different metrics); free-form JSON without type bridging (rejected: render-time errors).
- **Rationale:** A backlog needs urgency/importance/risk; bugs need severity/age/customer-impact; ideas need feasibility/novelty. Same engine, different mappings. Type bridging catches mismatches early.
- **Decided by:** malte.
- **Status:** active (lands in BL-032, v0.5).
- **References:** [ARCHITECTURE.md §3 "The Compass"](./ARCHITECTURE.md), [BL-032](./blitzlist/items/BL-032-compass.md).

## 2026-05-29 — Hierarchy via `parent_id` + hybrid state aggregation

- **Decision:** Items support unlimited-depth nesting via `parent_id`. UI renders full depth with drill-down (URL becomes that subtree's root; breadcrumbs zoom out). Parent state aggregation is HYBRID: parent has its own manual state, UI rolls up children as progress display, warns when parent state contradicts rollup.
- **Alternatives considered:** Two-level only (rejected: limits planning depth); auto-derived parent state from children (rejected: rigid; manual control more flexible); independent parent/child states with no rollup (rejected: loses "goal progress at a glance").
- **Rationale:** Top-down planning (goal → action → detail) is the dog-food workflow. Hybrid model preserves human authority while giving visual feedback.
- **Decided by:** malte.
- **Status:** active (lands in BL-031, v0.5).
- **References:** [ARCHITECTURE.md §3 "Hierarchy"](./ARCHITECTURE.md), [BL-031](./blitzlist/items/BL-031-hierarchy-and-attachments.md).

## 2026-06-01 — License: AGPL-3.0 + CLA + commercial tier

- **Decision:** Blitzlist is licensed under AGPL-3.0. Contributors sign a CLA (via CLA Assistant on GitHub) granting the project the right to dual-license. Commercial license tier available for enterprises that legally can't use AGPL.
- **Alternatives considered:**
  - MIT (rejected: no SaaS protection, weak acquisition story).
  - Apache 2.0 (rejected: same SaaS-protection gap; better patent grant but doesn't enable dual-licensing revenue).
  - n8n Sustainable Use License (rejected: not OSI-approved; we lack n8n's product gravity to absorb the credibility cost).
  - SSPL (rejected: too aggressive pre-launch; smaller community).
  - FSL-1.1-Apache (Sentry's 2-year auto-convert) (considered, still viable later).
  - DCO instead of CLA (rejected: blocks future relicense; one-way door).
- **Rationale:** AGPL preserves OSI-approved "true open source" credibility for HN launch. CLA preserves all future relicensing options (the move MongoDB and HashiCorp both made when leverage existed). Commercial tier creates revenue line and acquisition story. Track record: every successful OSS exit had CLA + commercial tier or open-core.
- **Decided by:** malte (after acquisition-lens research).
- **Status:** active. **TODO before public push:** populate `CLA.md` with Apache CCLA template; configure CLA Assistant on GitHub.
- **References:** [LICENSE](./LICENSE), [CONTRIBUTING.md](./CONTRIBUTING.md), [README.md §License](./README.md).

## 2026-06-01 — Expression indexes via raw SQL migrations

- **Decision:** Drizzle's SQLite emitter mangles JSON-path expression indexes (it backtick-wraps the SQL fragment incorrectly). Workaround: keep the Drizzle schema declarative for normal tables/indexes; expression indexes (e.g., `idx_items_priority` on `json_extract(custom_fields_json, '$.priority')`) live in hand-written raw-SQL migrations.
- **Alternatives considered:** Patch the generated migration manually each time `db:generate` runs (rejected: brittle; will break on regen); skip expression indexes entirely (rejected: critical for Compass + filtering performance); switch to a different ORM (rejected: too disruptive for a known workaround).
- **Rationale:** Pragmatic split — Drizzle controls what it can express cleanly, raw SQL covers what it can't. The schema file documents the workaround. Worth a Drizzle upstream issue but not blocking.
- **Decided by:** Claude (discovered during BL-004 implementation), malte (accepted).
- **Status:** active.
- **References:** [packages/db/src/schema.ts](./packages/db/src/schema.ts) (see the workaround note on `items`), [apps/api/migrations/0001_expression_indexes.sql](./apps/api/migrations/0001_expression_indexes.sql).

## 2026-06-01 — Canonical install URL: `https://mcp.blitzlist.ai/mcp`

- **Decision:** The production install URL for the Blitzlist MCP server is `https://mcp.blitzlist.ai/mcp` — dedicated subdomain + conventional `/mcp` path suffix. Old `api.blitzlist.ai/mcp` URL is dead (the dashboard's Custom Domain flow replaced rather than added when `mcp.blitzlist.ai` was set up; we committed to mcp.blitzlist.ai going forward).
- **Alternatives considered:**
  - `https://mcp.blitzlist.ai` — bare root, no path, cleanest aesthetically. **Tried and reverted**: see investigation below.
  - Keep `api.blitzlist.ai/mcp` alongside (rejected: api.blitzlist.ai is NXDOMAIN; not worth re-adding for backward compat).
- **Investigation note (the root-URL attempt and why it failed):** Initial plan was `apiRoute: ['https://mcp.blitzlist.ai/']` (host-wide protection) so the install URL could be the bare root. The `workers-oauth-provider` library DOES correctly serve `/.well-known/*` before apiRoute matching, but it does NOT carve out the configured `authorizeEndpoint` from apiRoute. Result: `POST /oauth/authorize` got 401-gated, blocking the consent screen entirely. Reverted to path-only `apiRoute: '/mcp'`. The cleanest user-facing URL is therefore `https://mcp.blitzlist.ai/mcp`.
- **Rationale:** Dedicated subdomain still wins on clarity ("this IS the MCP server") even with the `/mcp` suffix. When we add the REST API for the web UI in v0.5+ (BL-013), `api.blitzlist.ai` can be re-introduced for that purpose.
- **Decided by:** malte (after Claude proposed and tested the root-URL variant).
- **Status:** active.
- **References:** [apps/api/src/index.ts](./apps/api/src/index.ts) (`apiRoute: '/mcp'`). Worker fallback URL `https://blitzlist-api.damp-glade-177b.workers.dev/mcp` also works.

## 2026-06-01 — Auth resolver in `packages/core`, transport-agnostic; Hono middleware wraps it

- **Decision:** All auth lookups (v0.1 spike token, future OAuth, stakeholder keys, share codes) resolve into a single `RequestContext` type in `packages/core/auth.ts`. The Hono middleware in `apps/api/src/middleware/` is a thin wrapper that turns auth errors into 401s and sets `ctx` on Hono Variables. Tool handlers consume `c.get('ctx')` without knowing how the caller authenticated.
- **Alternatives considered:**
  - Auth logic inside Hono middleware directly (rejected: tight coupling to Hono; harder to test; harder to swap auth methods).
  - Multiple context types per auth method (rejected: tool handlers would need to branch on auth_method).
- **Rationale:** Tool handlers should be agnostic to auth method. A v0.1 spike-token caller, an OAuth-authenticated user, a stakeholder with a scoped key, and a share-code visitor all produce the same `RequestContext` shape — different `actor` discriminator + different `scope`. Tool handlers see `ctx.workspace_id`, `ctx.actor`, `ctx.permissions` and dispatch accordingly. When OAuth lands in BL-010, only `packages/core/auth.ts` and the middleware grow new branches — no tool code changes.
- **Decided by:** Claude (proposed), malte (accepted through BL-008 implementation).
- **Status:** active.
- **References:** [packages/core/src/auth.ts](./packages/core/src/auth.ts), [apps/api/src/middleware/spike-auth.ts](./apps/api/src/middleware/spike-auth.ts), [BL-008](./blitzlist/items/BL-008-token-paste-auth.md).

## 2026-06-01 — Hand-roll MCP protocol (instead of `@modelcontextprotocol/sdk`) for v0.1

- **Decision:** Implement MCP wire protocol by hand in `packages/mcp/` rather than depending on `@modelcontextprotocol/sdk`. Cover the four method handlers needed for v0.1 (`initialize`, `tools/list`, `resources/list`, `prompts/list`) plus notification + error paths. Adopt the official SDK in a later item when the tool surface grows enough that Zod-validated schemas + resource subscriptions justify the bundle weight.
- **Alternatives considered:**
  - Use `@modelcontextprotocol/sdk` from day one (rejected for v0.1: heavyweight for zero tools; the SDK is designed primarily for Node-based stdio transports and would need adapter work on Workers; bundle-size cost not yet justified).
  - Wait to ship `/mcp` until v0.5 when tools land (rejected: spike acceptance test requires the install handshake to work end-to-end).
- **Rationale:** MCP spec 2024-11-05 is well-defined JSON-RPC 2.0 with four list-style methods. Hand-roll is ~150 lines, fully typed, no runtime cost. We get full control over Hono integration. The SDK can be swapped in later by replacing `packages/mcp/server.ts` — the public API (`handleMcpMessage(message, ctx)`) is what apps/api consumes, and that contract doesn't change with the implementation.
- **Decided by:** Claude (proposed), malte (implicit through BL-005 acceptance).
- **Status:** active.
- **References:** [packages/mcp/src/protocol.ts](./packages/mcp/src/protocol.ts), [packages/mcp/src/server.ts](./packages/mcp/src/server.ts), [BL-005](./blitzlist/items/BL-005-mcp-server-skeleton.md).

## 2026-06-02 — Batch comments in list_items (kill the N+1)

- **Decision:** `list_items` (both workspace `/mcp` and stakeholder `/s/mcp` + `/c/<code>/mcp` versions) now returns comments inline per item by default. Each returned item gets a `comments` array (latest N normalized comments — `{id, author, body, created_at}`) and a `comment_count` (total, regardless of limit). Single batched query for all the comments per `list_items` call — `SELECT * FROM comments WHERE item_id IN (...) ORDER BY created_at DESC` — grouped + sliced in JS. Two new params: `include_comments` (boolean, default `true`) and `comments_limit` (0-50, default `5`).
- **Why:** triggered by malte hitting the same N+1 pattern previously seen with state — agents had to call `get_item` per item to pull comments, leading to N approval prompts per "show me the list with comments" user request. Batch fetch closes that loop.
- **Alternatives considered:**
  - Always include 5 comments, no toggle (rejected: makes the response heavy for callers that don't need it; opt-out is one boolean).
  - Per-item recent activity too (rejected for this round: activity rows can be noisy and large; comments are the one external/conversational signal that's almost always interesting alongside the item).
  - SQL-side window/partition for "latest N per item" (rejected: D1's SQLite supports window functions but the JS-side group+slice is clear, bounded, and the comments table is small at our scale).
- **Status:** active. 22 v0.5 MCP tools unchanged in count; two of them got new optional params. Worker version `d60a67a5-…`.
- **References:** [apps/api/src/tools/list-items.ts](./apps/api/src/tools/list-items.ts), [apps/api/src/tools/stakeholder/list-items.ts](./apps/api/src/tools/stakeholder/list-items.ts).

## 2026-06-02 — Interactive share codes (comment/edit/create on the web)

- **Decision:** Extend share codes (BL-030) beyond read-only with three new permission tiers — `comment`, `edit`, `create` — and surface them as interactive forms on the public `/r/<code>` web page. The 4-word URL credential continues to be the auth: anyone with the link gets exactly the permissions configured on the code. Edit means visitors can update item state via a dropdown; create means visitors can add new items via an "+ Add a new item" form at the bottom of the list; comment means each card gets an "Add a comment" expandable form. A "Sign your activity as <name>" optional field stores the visitor's display name in a `blz_name` cookie (90 days, SameSite=Lax, Secure) and is then prefilled across all the forms.
- **New routes (all on the same share-code-in-URL credential model):**
  - `POST /r/:code/identify` — sets/clears the display-name cookie, redirects back
  - `POST /r/:code/comment/:item_id` — anonymous-but-attributed comment (uses display name if set; falls back to `Anonymous via <first-word-of-code>…`)
  - `POST /r/:code/state/:item_id` — state transition via dropdown
  - `POST /r/:code/new-item` — adds item to the first list in scope; auto-applies template defaults
  - All use POST→303-redirect (PRG pattern) to avoid double-submit; flash messages via `?flash=ok|error&msg=...`

- **Decision:** Reshape the entire data model from Linear-shape (items live in one list, list owns state machine) to Airtable-shape (templates own schemas; lists are universal containers; items carry typed fields validated against their own template; items↔lists is many-to-many with per-list `role` + `position`). Triggered by user reflection that "release = list" was the right intuition but didn't go far enough — the real reframe is that lists/groups/PRDs/sprints/releases/shopping-lists/invite-lists/wishlists are all the same primitive. The Linear-shape was a category error for Blitzlist's positioning. Migration `0004_airtable_shape.sql` is destructive (spike data dropped, no production users to preserve). Refactored 9 existing tools, dropped 3 (`create_release` / `promise_in_release` / `close_release`), added 6 new (`update_item`, `list_templates`, `create_list`, `close_list`, `add_item_to_list`, `remove_item_from_list`). Total: **12 v0.5 MCP tools live**, all with annotations.
- **Alternatives considered:**
  - Keep current Linear shape; document Airtable as v0.5 target (rejected: more code to untangle later; the schema-pitch mismatch was actively making implementation drift worse).
  - Half-measure: drop `items.promised_in` but keep `groups`+`item_groups` (rejected: leaves the lists/groups duality that caused the confusion in the first place).
  - "Release = list with target_date" only, keep everything else (rejected after deeper reflection — the universal-primitive insight applies to ALL list kinds, not just releases).
  - Defer all schema reshape to a single v0.5 migration just before shipping (rejected: forces a much bigger destructive change later when there might be real users).
- **Rationale:** The founding pitch says *"In boardrooms. In family kitchens. In sprint plans. In grocery shopping."* — every one of those needs different *columns*, not different products. Templates own field schemas; items inherit a template at creation but carry it independently; lists are containers with optional template suggestions. State becomes "just a field" (single_select with terminal-flagged options) — `set_state` survives as a convenience wrapper. Position moves to `item_lists` (per-list ordering). Responsible/accountable become user-typed fields in templates (per-template, per-list). All five group types (sprint/milestone/epic/label/release) collapse into one list primitive distinguished by `template_id` + `role` on the membership row. 10 system templates seeded per workspace: backlog, bugs, todos, ideas, release, sprint, shopping, wishlist, invite, picnic.
- **What changed concretely:**
  - **New tables:** `templates` (workspace-scoped schemas), `item_lists` (many-to-many join with `role` + `position`)
  - **Dropped tables:** `groups`, `item_groups` (folded into `lists`)
  - **`items` reshape:** dropped `list_id`, `position`, `assignee_id`, `state`, `promised_in`; added `template_id`, `fields_json`
  - **`lists` reshape:** dropped `states_json`, `fields_json`, `template_id (text)`, `default_view`; added `template_id (FK)`, `meta_json`, `tags_json`
  - **New activity actions:** `item.field_changed`, `item.added_to_list`, `item.removed_from_list`, `list.closed`, `template.created`, `template.field_added/removed/updated`
  - **Field type system in `packages/core/fields.ts`:** text, long_text, number, date, single_select (with terminal), multi_select, checkbox, url, user, link_to_item, attachment, formula (deferred to v1.0)
- **Decided by:** malte (reflection that drove the redesign), Claude (proposed concrete schema, implemented).
- **Status:** active. Supersedes BL-010's release-specific shape. Worker version `266f950e-…`.

## 2026-06-01 — BL-010 complete: release type + commitment ledger

- **Decision:** Releases are the headline-wedge primitive — one of five group types (`sprint|milestone|epic|label|release`) in a new `groups` table, joined to items via `item_groups`. Releases also get a first-class `items.promised_in` column (separate from generic `item_groups` membership) so the commitment ledger is a real foreign key, not a tag. Three MCP tools: `create_release` (slug+name+version+ship_target), `promise_in_release` (item ↔ release with re-promise semantics), `close_release` (computes delivered/slipped/cut, persists breakdown into `groups.meta_json.breakdown`, emits `release.closed` activity). Closed releases are immutable; re-calling `close_release` returns the stored breakdown verbatim. Cut > delivered > slipped precedence in the auditor.
- **Alternatives considered:**
  - Make releases a custom-field on items (rejected: no first-class queries, no closed_at lifecycle, breakdown can't be persisted cleanly).
  - Compute breakdown on every read instead of persisting (rejected: closed releases must show the breakdown that was true *at close time*, not the current state — items keep moving after close).
  - One tool `update_release` that handles create/promise/close (rejected: MCP tool clarity beats fewer tools; each release transition is a different audit-log event).
  - Skip `items.promised_in` and use `item_groups` rows for releases too (rejected: releases are the commitment column, deserving of a real FK; the other group types are tags by comparison).
  - Add a `reopen_release` tool (rejected for v0.5: not in BL-010 acceptance criteria; can be added later if real workflows demand it).
- **Rationale:** The "commitment-to-delivery loop" is the unique wedge from the competitive analysis — no tool today shows what was promised, what shipped, what slipped, what was cut. Making release a real type (not a label) gives `close_release` a place to store the breakdown forever. Releases reference items by ID in the breakdown so even renamed/deleted items keep their historical position. Cut-overrides-delivered precedence handles the edge case where the closer wants to remove a done item from the release notes for narrative reasons. The release-notes generator (BL-017) reads the persisted breakdown — no recomputation needed.
- **Decided by:** Claude (proposed), malte (accepted through BL-010 acceptance).
- **Status:** active. Nine v0.1 MCP tools now live: `add_item`, `list_items`, `get_item`, `set_state`, `comment`, `set_executor`, `create_release`, `promise_in_release`, `close_release` — all with annotations. Tables in remote D1: 11.

## 2026-06-01 — BL-009 complete: executor field + set_executor tool

- **Decision:** Items get an `executor` field — a free-text discriminator saying who/what is currently doing the work, distinct from `assignee_id` (the accountable human). Format: `human:<uid>` | `agent:claude` | `agent:<name>` | `self` | `contractor:<label>` | `null`. New MCP tool `set_executor` writes it; `add_item` accepts it optionally and falls back to a template-driven default; `list_items` filters by it. The literal `"self"` is materialized to `human:<uid>` at write time so the audit trail stays meaningful when the executing actor later changes. Default-executor mapping (in `packages/core/executor.ts`): `bugs → agent:claude`, `todos → self`, `ideas → self`, everything else → `null`.
- **Alternatives considered:**
  - Use `assignee_id` to mean both accountable + executing (rejected: collapses the most interesting distinction in hybrid-team work — accountable human ≠ doing-it-right-now agent).
  - Strongly-typed enum for executor values (rejected: contractor labels are open-ended; agent names will multiply; free text with a validator is more honest).
  - Auto-spawn a Claude session when `executor` becomes `agent:claude` (rejected for v0.5: declarative-only — agent spawning is BL-018's job and gets opt-in semantics in v1.0).
  - Resolve `"self"` lazily on read (rejected: breaks the audit trail; if Malte sets `executor: "self"` and the workspace is later transferred, the historical activity log should still say `human:usr-malte`).
- **Rationale:** Executor is the foundation of the "self-solving" feature — items get routed to whoever should handle them (default per template), agents and humans coexist in the same field, and state moves regardless of who/what executes. Free-text format keeps the door open for future executor kinds without schema changes. Tool-layer validation (`parseExecutor`) gives clear errors. Activity log captures every transition with from/to + optional note. `idempotentHint: true` on `set_executor` matches `set_state` semantics — repeated calls are no-ops but still log.
- **Decided by:** Claude (proposed), malte (accepted through BL-009 acceptance).
- **Status:** active. Six v0.1 tools now live: `add_item`, `list_items`, `get_item`, `set_state`, `comment`, `set_executor`.
- **References:** [packages/core/src/executor.ts](./packages/core/src/executor.ts), [apps/api/src/tools/set-executor.ts](./apps/api/src/tools/set-executor.ts), [apps/api/migrations/0002_items_executor.sql](./apps/api/migrations/0002_items_executor.sql), [BL-009](./blitzlist/items/BL-009-executor-routing.md).

## 2026-06-17 — Agent tokens: headless write access without OAuth (BL-023)

- **Decision:** Headless agents (e.g. Hermes) authenticate with a static `blz_at_` bearer token at a dedicated `/a/mcp` endpoint, resolving to the full workspace context (acting as the minting owner) but routed to a curated create/edit/share tool subset — NO admin tools (can't mint/revoke keys or revoke share codes). Owner mints via `create_agent_token` on OAuth `/mcp`. Tokens are bound per-workspace. New `agent_tokens` table, separate from `stakeholder_access_keys`.
- **Alternatives considered:**
  - Have the agent complete the OAuth flow once and cache the token (rejected: headless agents have no browser for the interactive consent step).
  - Extend stakeholder keys (`/s/mcp`) with write tools (rejected: stakeholder keys are external + list-scoped and conceptually can't create new lists; "create/share" are workspace-level ops).
  - Full owner-equivalent token, all 32 tools (rejected by malte: agent shouldn't be able to escalate/manage access).
- **Rationale:** Reuses the proven stakeholder-key crypto/storage pattern (sha256, prefix, expiry, revoke) but with a distinct prefix + endpoint + table so the two bearer paths can't cross over. The registry IS the capability boundary — an agent token literally cannot see admin tools. Owner attribution in the activity log is honest (the owner delegated).
- **Decided by:** malte (chose "create/edit/share, no admin" from the scope question), Claude (proposed the PAT-style design).
- **Status:** active.
- **References:** [apps/api/src/tools/agent/index.ts](./apps/api/src/tools/agent/index.ts), [apps/api/src/tools/create-agent-token.ts](./apps/api/src/tools/create-agent-token.ts), [packages/core/src/agent-token.ts](./packages/core/src/agent-token.ts), commit af1d500.
